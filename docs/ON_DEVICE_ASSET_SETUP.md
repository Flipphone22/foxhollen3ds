# On-device setup and startup menu

User requirement added12October. This is part of the active port goal, not a
replacement for rendering correctness and performance work. The intended install
is the shared application plus the user's own PAL revision1ISO at
`SD:/3ds/foxhollow/disc.iso`. No host Python, asset transfer bundle or separate
probe application should be required for the completed workflow.

Current status: **native source reader/fingerprint, source-record decoder,
conversion journal, bounded cache converter, ISO texture enumeration and
resumable native texture-pack conversion, full original ISO geometry compilation
and resumable geometry-pack output, preset definitions and portable menu state
are implemented locally. The ISO-to-native-reduction and paired topology/geometry
pipeline also passes focused host and ARM checks; see
[Native asset reduction](NATIVE_ASSET_REDUCTION.md). Native movie decoding,
resizing, encoding and resumable assembly are implemented and undergoing full
conversion checks; see [Native movie preparation](NATIVE_MOVIE_PREPARATION.md).
The task/menu controller, SDK screen wrapper, final bundle publication layer and
real four-stage conversion task are implemented locally. The task passes partial
source-fixture cancellation/resume tests and a complete ARM SDK link. Generated
recipe identities, committed runtime paths and a conditional normal-entry
integration now exist. The copied entry compiles and setup modules link together;
the full executable, installation and screen/game handoff are unvalidated.** See
[Installation bundle](INSTALLATION_BUNDLE.md). Existing normal
and replay builds/installations are unchanged. Do not advertise ISO-only setup
as working or display a completed conversion before all required outputs exist.

The startup menu must show the build/source ID, preparation status and real
per-stage progress. It offers Start game, Prepare/resume assets, Graphics preset,
Diagnostics and Exit. Preparation is needed once per incompatible asset recipe,
not once per application build. A build ID and an asset-format/recipe identity
are different things. Updating rendering code alone must not force hours of
reconversion. Normal startup should use a compact committed manifest, not scan
and hash every generated byte again.

The five presets are `n3ds-fancy`, `n3ds-fast`, `o3ds-fancy`, `o3ds-fast`, and
Custom. Selecting a named preset updates existing graphics bits and original
geometry/texture choices before those resources load. Custom preserves the
user's per-effect settings. FPS/performance/counter displays remain independent.
Existing settings and saves must not be overwritten by an automatic hardware
default. The initial definitions are provisional quality choices, **not measured
performance promises**:

| Preset | Geometry/textures | Optional effects |
|---|---|---|
| n3ds-fancy | Original/original | Particles, weather, diffuse maps, height fog, specular, source fur/groom, splash/drop effects, shape shadows |
| n3ds-fast | Performance/performance | Particles, weather, diffuse maps; shadows off |
| o3ds-fancy | Original/performance | Particles, weather, diffuse maps, height fog, splashes; shadows off |
| o3ds-fast | Performance/performance | Particles and weather; shadows off |
| Custom | Retained user choices | Retained user choices |

All named presets retain world, actors, textures, HUD, sky, movies, holograms,
lighting and morphs. Fast geometry still must pass the existing shape, UV,
bone-blend and navigation guards; a preset cannot authorize broken geometry.
Source textures and source geometry remain independent choices. Effects remain
disabled by their actual compute gates, not merely hidden after doing the work.

Preparation design requirements:

1. Read the ISO directly through one owned, read-only source handle before game
   startup. Enumerate its FST once. Do not extract thousands of raw files or
   introduce per-frame directory lookups. The pinned Melee file-I/O implementation
   documents costly FAT directory opens; its bounded indexed-reader principle
   is retained, adapted to an ISO/FST source rather than a flat extracted tree.
2. Process one bounded original record/model/movie frame at a time. Native
   compilation must preserve all current topology, UV, palette, morph, source
   reference, material, coverage and lifetime invariants. Do not reconnect a GX
   interpreter to the per-frame renderer. Loading-time compilation is distinct
   from the retired rendering architecture.
3. Generate both original and accepted performance resources needed by the
   presets: topology packs, persistent PICA geometry and palette partitions,
   block caches, PICA texture packs/quantization, and the prepared movie stream.
   Preserve THP audio and frame timing. C/C++ native codecs replace host tools;
   an installed Python interpreter or preconverted user bundle is not the end state.
4. Use recipe-versioned staging on SD. Record completed output/source checksums,
   bounded stage/unit cursors and source identity so cancellation/power loss can
   resume. Validate each artifact before publication and commit the complete
   generation last. Preserve the previous usable generation until commit.
   Never treat a partial file's existence as successful conversion.
5. Scope cleanup strictly to generated staging paths. Keep `disc.iso`, saves,
   recording fixtures and graphics preferences private and untouched. Report
   insufficient space or malformed input explicitly; do not silently publish
   reduced/empty coverage as success.
6. Progress comes from the converter's actual completed units. Unknown work
   displays “Calculating work”; reaching100% for one stage does not mean all
   preparation is finished. Cancellation keeps ownership until the converter
   has safely stopped and its checkpoint is committed.
7. Integrate future specific hardware probes into Diagnostics with their build
   identity and log output. They must retire GPU work/resources before returning
   to the menu or starting gameplay. Dangerous probes remain explicit opt-in;
   routine launches do not execute them. The latest hardware sky UV run has been
   collected and verified; no further standalone sky probe is needed for that
   fault. Future diagnostics belong in this menu.

## Native transaction and first conversion stage

`install_transaction.c` writes recipe-owned artifact IDs within separate
`generated/gXXXXXXXX` directories. Two checksummed journal slots record flushed
prefixes and source cursors; two separate activation slots select complete
generations. The recipe owner supplies both 32-byte recipe and source identities.
The native fingerprint task derives the source identity; connecting it to the
complete recipe owner is still integration work.
The FST checksum alone is insufficient.

Completed outputs are CRC-checked on preparation resume and before publication,
with a stage-specific semantic validator at artifact completion. Ordinary active
generation lookup checks committed metadata, file existence and sizes without
rehashing all assets. Uncommitted output tails are truncated on resume. Recovery
also handles a finalized filename whose completion checkpoint was interrupted.
Header rewrites are allowed only before a nonempty durable checkpoint; the final
checksum is recomputed after such a rewrite. Explicit restart creates a fresh
generation after damaged pending output, retaining old files and active assets.
Generation cleanup/space estimation and the final UI retry flow are still open.

This adapts the pinned Melee `port/3ds/card_storage.c` temporary-write/previous-copy
principle to a multi-file asset generation. It does not modify game saves.
The libctru archive device maps `fsync` to FSFILE_Flush and `ftruncate` to
FSFILE_SetSize; see its [archive device implementation](https://github.com/devkitPro/libctru/blob/master/libctru/source/archive_dev.c).
Those calls and host fault tests do not establish physical power-cut durability
of every FAT operation. No such hardware claim is made.

`install_cache.c` replaces `prepare_block_cache.py` with a native, 64 KiB-block
LZ4 encoder. It consumes a previously completed prepared artifact, generates the
existing FHBCACH1 format and validates it with the actual bounded runtime decoder.
It supports fast compression or HC levels3–12. The native geometry compiler that
will produce that input directly from the ISO is not implemented yet. This stage
does **not** make ISO-only installation complete.

Cache progress reports actual uncompressed bytes after each block and permits
cancellation. The interrupted cache stage restarts from zero; earlier completed
stages remain retained. That is stage-level resume, not per-block cache resume.
Conversion scratch is capped at512 KiB; it is freed before the separate256 KiB
validation cache is allocated. A changed source checksum aborts publication.
No gameplay worker, frame-loop I/O, GPU allocation or renderer change is added.

`test_install_transaction.py` passes ASan/UBSan and ARM compilation with prefix
rollback, rename interruption, failed flush, output corruption, both activation
slot preservation, fresh restart, 192 manifest mutations, 192 truncation sizes,
header rewrite/append/resume and checkpointed-prefix protection. It exercises
actual transaction functions, not a Python simulation of them.

`test_install_cache.py` passes ASan/UBSan, actual ARM compilation and a relocatable
link against the installed ARM liblz4. Seven cases match the host recipe byte for
byte with the same host codec: small/raw/compressed/incompressible/boundary/mixed
inputs and a private42,800,384-byte scene pack. The latter produces18,359,073 bytes
with404,041 bytes of measured explicit heap and655 progress callbacks. Cancellation
and a changed input are rejected/recovered as intended; input bytes are preserved.
The measured heap excludes libc/stdio internals and stack. ARM code has been linked,
not executed here; byte identity across different LZ4 versions is not asserted.

Evidence: `artifacts/research/install-transaction-test/result.json` and
`artifacts/research/install-cache-test/result.json`. No full app build, emulator
FPS claim, deployment or physical conversion timing exists for these modules yet.
App integration must add `-llz4` to the reproducible shared build and include all
startup units; the relocatable component link alone does not update the app.

## Native texture encoding

`install_texture.cpp` implements bounded CMPR-to-PICA ETC1/ETC1A4 encoding, using
the same high-quality `rg_etc1` codec as the pinned desktop tex3ds v2.3.0 recipe.
The native adapter does not require PNG, Magick or the desktop frontend. The
codec's separate ZLIB license, provenance and local portability fixes are in
`native-3ds/vendor/rg_etc1` and `native-3ds/licenses/ADAPTATIONS.md`.

Caller-owned source/output buffers are at most512 KiB/1 MiB. There is no full
RGBA intermediate image or dynamic allocation inside the kernel. Its codec
tables occupy33,040 bytes of BSS, plus one adapter initialization byte; these
would remain resident if linked into the app. The ARM compiler reports23,337
bytes of codec text and2,544 of adapter text. Stack-use files record individual
functions, not an observed full call-chain peak. Overall startup and gameplay
budgets must include these costs when integrated.

Power-of-two original images8..1024 are supported. Reduced variants are opaque
only, preserving the existing separable BOX rounding. Original dimensions,
source identity and alpha coverage must remain recorded by the future pack
writer. The kernel reports squared RGB error against the full/filtered target;
the recipe must retain the current RMSE14 gate. It reports actual completed
8x8tiles and accepts cancellation between them; cancelled output is incomplete.

`test_install_texture.py` matches34existing private full/reduced textures exactly
against their deployed ETC bytes and independently checks alpha and error sums
with the runtime decoder. Short/overlapping buffers, invalid dimensions,
transparent reductions and cancellation are checked under ASan/UBSan. ARM
compilation passes. The selected targets are at most256pixels per dimension,
so this is not proof of all source-record coverage or1024texture execution.

The first check exposed undefined negative float-to-unsigned refinement casts
in the upstream codec and an alpha texture mismatch. Signed conversion before
clamping fixes the UB. Matching the desktop loader's transparent-canvas
compositing fixes the latter: hidden RGB is zeroed before encoding, while alpha
coverage stays exact. Nine explicit uint32_t template arguments address the
newlib typedef difference. These adaptations are marked and retained with source
hashes; failures are not counted as accepted results.

The following pack-writing stage now connects this kernel to conversion
transactions. Texture-bank enumeration and actual console startup integration
remain missing. No ARM execution or console conversion-time claim is made.

## Resumable native texture-pack writing

`install_texture_pack.c` encodes each supplied CMPR image once into a checksummed
intermediate spool artifact. It stores original bytes, accepted full/reduced
payloads, dimensions, CRCs and measured errors. The existing RMSE14 limit is
enforced here; rejected candidates remain explicitly recorded and retain source
identity. The existing native original-image conversion still handles images
that are unsuitable for ETC compression. This does not reconnect old rendering.

Each completed image has a durable transaction checkpoint and caller-supplied
next-source cursor. After interruption, only the current unfinished image needs
re-encoding. Duplicate checks compare exact source bytes after matching CRC and
dimensions, including for rejected candidates. Changing the reduction recipe
within a spool is rejected. Progress distinguishes original and reduced encoding
phases and uses actual completed tiles. The kernel has no rendering/frame work.

The assembler reads the completed spool, sorts the directory and writes the
existing FHTXPK2 format. It preserves full-size and reduced variants separately.
Its immutable header precedes entry checkpoints, so assembly resumes without
re-encoding earlier images. The actual runtime pack reader and full source/GPU
checksums validate the output before publication. No partial file is ready.

Caps:4,096 unique source records,4,096 output entries,128 MiB per spool/pack.
Exceeding a cap fails explicitly. The intermediate remains in the generation;
cleanup, total SD-space estimation and whole-recipe artifact-slot allocation
are pending. The current transaction has eight slots and this stage uses two.
The staging directory allocates212,992 bytes. Largest-image encoding can also
require1 MiB full-output plus128 KiB reduced-output scratch, in addition to
caller input, codec tables, stdio and stack. Those buffers are bounded, not a
measurement of the complete ISO installation's peak.

`test_install_texture_pack.py` exercises the real codec, transaction owner,
spool/assembler and runtime reader with six existing private textures and two
constructed equal-CRC/different-byte textures. Eight full plus two reduced
entries match the previous assets/independent SDK tex3ds bytes. A high-frequency
red/blue source fails the quality gate explicitly. Duplicate calls do no encoding
or payload writes. Cancellation while encoding the next image retains prior
work; assembly cancellation resumes at its next entry. A corrupted pending
spool fails while the previous committed generation remains usable.

The ASan/UBSan run measured286,720 bytes of explicit native heap, excluding
caller source fixtures, libc/stdio, stack and33,041 bytes of codec/adapter BSS.
The resulting186,400-byte pack is a **private bounded test fixture**, never a
replacement for the complete game pack. Actual ARM C compilation and a combined
relocatable link with the checked ARM C++ encoder pass; this is not ARM execution.
The app source hash now includes `.cpp`, covering future codec changes.

Evidence: `artifacts/research/install-texture-pack-test/result.json`,
`sources.json`, `arm-undefined.txt`, `build-source-hashes.json` and the private
test pack. Original ISO texture enumeration, complete coverage/space/memory

## Native ISO texture preparation

`install_texture_iso.c` enumerates indexed TEX banks directly from the borrowed
read-only ISO. It interprets the original direct/frame table entries, processes
one compressed source record at a time, and feeds the native spool/pack writer.
No extracted directory tree, Python, PNG or desktop image library is required
by this C/C++ conversion path. The driver releases its scan buffers before final
pack assembly and never activates an incomplete whole-game generation.

Source coverage was independently checked against the existing host recipe:
107 banks,3,899 eligible CMPR records,1,135 unique images,17,957,568 unique source
bytes. Every eligible host record is covered by the indexed table; exact ordered
dimensions/source CRCs match the native scanner over the entire ISO. One short
TEXPRE stored preload wrapper is explicitly counted and skipped, matching the
host recipe, rather than incorrectly treating it as a96-byte texture header.
Other source formats are outside this ETC preparation stage; this is not a
claim that every original texture format has become ETC.

Scan bounds:256 banks,8,192 record offsets per bank,64 KiB texture table, plus
one decoded/compressed record under the existing caps. The actual maximum
table-covered records per bank is417. Resume accepts only exact source record
boundaries and validates their original extents.

## Incremental source identity

`install_fingerprint.c` uses the SDK mbedTLS SHA256 API,64 KiB of ordinary heap
and one block per caller-driven step. The menu owner can update byte progress
and process cancellation between steps. The task exclusively borrows the ISO
cursor, restores it on completion/cancellation, and exposes a digest only after
the entire source was read successfully. Truncation, size changes, cursor
interference and read failures invalidate the result. It cannot detect an
external writer changing already-read bytes without changing file size; source
ownership must exclude concurrent mutation during preparation.

The actual owner matches Python SHA256 for ten boundary-length fixtures and the
entire1,459,978,240-byte PAL ISO in22,278 bounded steps. Cancellation/restart and
failed reads are checked under ASan/UBSan. ARM compilation and a relocatable link
with the installed SDK `libmbedcrypto.a` resolve the SHA functions; this is not
physical-console execution. No enum types cross that API despite SDK object
enum-size warnings. The eventual app must link that dependency. Ordinary game
startup uses committed metadata rather than rerunning the full fingerprint.

original corner references, including both UV sets, matrix slots, the synthetic

comparisons cover4,174,335 corners across all2,110 unique model/world sources,

## Original geometry directly from the ISO

`install_geometry_iso.c` enumerates indexed model and world banks through the
native FST reader. It owns one table (maximum64 KiB) and one decoded record
(maximum4 MiB), rather than extracting files or retaining whole banks. Resume
uses a validated FST bank ID and next table index. Root world-bank copies without
an index are excluded by the same rule as the existing host recipe. An indexed
unsupported record stops the integrated converter explicitly.

The actual PAL revision1 ISO contains109 indexed banks and4,613 eligible source
records, representing2,110 unique sources. Native enumeration matches the host
parser's ordered IDs, sizes and CRCs exactly. Resume and invalid-cursor checks,
ASan/UBSan and ARM compilation pass; no unsupported eligible sources were found.

`install_geometry_pack.c` adds a checkpointed `FHGSPL01` spool. Each unique
source records its runtime identity, SHA256, compiled packet and checksums.
Repeated sources reuse completed output; a CRC identity collision with a
different SHA256 fails explicitly. Non-rendering sources are recorded as such
after source validation. An interrupted append is truncated to its durable
checkpoint before resuming. Pack assembly writes the existing `FHNSSET1`
directory once and checkpoints each packet, without rewriting committed bytes.
Packets are checked with the actual native scene reader before completion.
Neither finishing the spool nor the geometry pack activates the whole game.

The complete original geometry conversion passed on PC:2,102 renderable packets
